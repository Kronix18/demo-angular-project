# Task 1.3 — Wire Real Guards & Fix Login Page

Status: NOT STARTED
Depends on: 1.1, 1.2
Goal: Protected routes actually redirect unauthenticated users to the REAL login route with a returnUrl; the login page's own nav links work (they currently reference a dead route and an unimported directive).

## Why (audit findings)
- `auth.guard.ts` redirects to `/login` — that route does NOT exist (real route is `/auth/login`), so guarded access would fall through to `**` → silently land on home.
- `app.routes.ts` uses `canActivate: [() => true]` placeholder guards on /screener, /profile, /stock/:symbol — the real authGuard is wired NOWHERE.
- `login.component.ts` template uses `routerLink` but imports only `[FormsModule]` → runtime error "Can't bind to 'routerLink'" in console; its links point to `/` and `/register` — `/register` is also a dead route (real: `/auth/register`).

## Test-first (RED)
1. `src/app/core/guards/auth.guard.spec.ts`: RouterSpy — logged-out → returns false + navigates to `/auth/login` with `returnUrl` query param; logged-in → returns true.
2. Extend `login.component.spec.ts`: template compiles WITHOUT the routerLink error (add `RouterLink` import), nav links point to `/auth/register` and `/home`.

Run `ng test` → FAIL (RED). Commit: `test: guard redirect + login page routerLink specs (RED)`.

## Implementation (GREEN)
- `auth.guard.ts`: `router.navigate(['/auth/login'], { queryParams: { returnUrl: state.url } })`.
- `app.routes.ts`: replace ALL `() => true` placeholders with `authGuard` on /screener, /profile, /stock/:symbol. `/charts/:symbol` stays public.
- `login.component.ts`: add `RouterLink` to imports; fix links to `/home` and `/auth/register`.
- After login success (1.1), navigate to `returnUrl` if present, else `/` (update login submit handler).

## Verification (browser)
- Logged out, open `/profile` → lands on `/auth/login?returnUrl=%2Fprofile`.
- Log in → returned to /profile.
- Login page console: NO routerLink binding errors.
- Screenshot redirect + post-login return.
