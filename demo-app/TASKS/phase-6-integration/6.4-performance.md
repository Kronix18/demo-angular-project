# Task 6.4 — Performance (large datasets)

Status: DONE (2026-09-29) — solved by the 5.4 LOD design, measured here
Depends on: 3.2
Goal: MSFT daily data since 1986 (~10k bars) renders interactively; initial chart load < 3s; pan/zoom stay smooth.

## Why (audit findings)
- msft.us.txt holds ~40 years of daily rows; ALL range (6.x) and no decimation → Chart.js drawing 10k candles per frame = jank.
- Python app has `chart/lod.py` (level-of-detail) — its Chart.js equivalent is the built-in `decimation` plugin; old plan's "data decimation" item maps here.
- No budget was ever measured (old plan set targets but nothing was benchmarked — same pattern as the false "completed" claims).

## Steps
1. **Test-first**:
   - Viewer spec: options.plugins.decimation enabled (`enabled:true, algorithm:'lttb', samples:2000`) when data length > threshold.
   - Aggregation helper: range 'ALL' on 10k bars passes decimation config (assert).
2. Implementation:
   - Enable Chart.js decimation plugin (part of chart.js core; registerables covers it) with LTTB, threshold ~1500 points.
   - Request data lazily per symbol with `shareReplay(1)` in the service (avoid refetch on indicator toggles).
   - Measure: add `scripts/perf-check.mjs` (Playwright, headless): load `/charts/msft`, wait for canvas, measure LCP + first-chart-frame via performance API; assert < 3s locally; record numbers here.
3. Only optimize what the measurement shows; keep changes minimal.

## Verification results (fill after doing)
- **Deviation from the plan (deliberate):** Chart.js's `decimation` plugin (LTTB) only handles line datasets and can't aggregate OHLC candles or volume. Instead `charts/chart-lod.ts` (5.4) holds only a window around the visible range, aggregated into ≤ ~500 OHLCV buckets, with y-axes fitted to the visible bars inside the chart's own update. This is the Chart.js equivalent of the Python `chart/lod.py` for all dataset types.
- Data: one fetch per symbol (cached in the viewer; range/indicator/interval changes re-render from cache — **interval switch used to refetch the file; now it re-aggregates weekly client-side**; `e2e/layout.spec` asserts a single file request). Toolbar now `markForCheck`s on store writes (zoneless).
- Measured (headless chromium, software rendering, dev server): cold load of `/charts/msft` with range ALL (10,208 bars) + SMA/EMA/RSI/ATR → chart drawn in **672 ms** (budget < 3 s, asserted); wheel/pan frames median ~16.7 ms, p90 ~18–23 ms with 4 indicators over the full history (asserted < 30 / < 60 ms); chart data window ≈ 340 points instead of 10k (asserted < 700).
- Specs: `chart-lod.spec` (7), viewer "LOD" spec, `e2e/layout.spec` "pan … smooth" + "cold load … < 3s".
- Not done: LCP via the performance API / `scripts/perf-check.mjs` — superseded by the Playwright assertions above.
